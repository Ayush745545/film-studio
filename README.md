# AI Film Studio

**A professional editor, an AI film studio and a production pipeline in one workspace.**

Idea → Story → Script → Characters → World → Scenes → Storyboard → Shots → Image → Video →
Voice → Sound → AI Edit → Pro Editor → Color → Export.

It runs with **zero configuration**: no API keys, no database, no ffmpeg. Everything is
generated by a built-in engine that produces *real* files — SVG plates, synthesised WAV audio,
procedural motion — each visibly labelled as demo media. Add provider keys and the same
pipeline starts producing real model output without a single UI change.

---

## Quick start

```bash
npm install
npm run dev                 # http://localhost:3000
```

Want a finished film to look at immediately?

```bash
npm run seed                # builds "The Last Memory": story → graded timeline → stems
npm run dev                 # open the project it prints
```

Production:

```bash
npm run build && npm start
```

Verified on Node 20. PostgreSQL, Redis, S3 and ffmpeg are all optional.

> **Heads-up on `npm run dev`:** dev-mode webpack holds the whole module graph in
> memory and wants roughly 2 GB. On a small container it can be OOM-killed while
> compiling — that looks like the server silently dying, not like a code error.
> Give it headroom (`NODE_OPTIONS=--max-old-space-size=2048 npm run dev`) or use
> `npm run build && npm start`, which is what this repo is verified against.

### Boot sequence

There is deliberately **no `instrumentation.ts`**. Next compiles that file for the edge
runtime as well, and in `next dev` the `process.env.NEXT_RUNTIME === 'nodejs'` guard is not
inlined — so webpack still follows the import and dies on the Node-only graph:

```
UnhandledSchemeError: Reading from "node:child_process" is not handled by plugins
node:child_process ← lib/media/ffmpeg ← lib/pipeline/export ← lib/queue/handlers
```

Instead, boot is lazy and idempotent in `src/lib/boot.ts`. `ensureBooted()` is awaited by the
API wrapper (and by the SSE, media and auth routes), installs the queue workers, seeds the
model registry, provisions the first profile and starts the scheduler. It behaves identically
in `next dev`, `next build`, `next start` and standalone output, and costs a few milliseconds
on the first request.

### Server-rendered first paint

Zustand v5 wires `getServerSnapshot` to `api.getInitialState()`, so anything written with
`setState()` during SSR is invisible to the server render — the page paints a loading state
and then swaps. Two consequences that are handled explicitly:

- **Selectors must be referentially stable.** `useApp(s => s.boot?.plans ?? [])` allocates a
  fresh array per call and produces *"The result of getServerSnapshot should be cached to
  avoid an infinite loop"*. Fallbacks are module-level constants; derived lists go through
  `useShallow` or `useMemo`; one primitive per selector.
- **Boot data reaches the first paint through React context**, not the store.
  `app/layout.tsx` resolves the payload server-side, `BootProvider` supplies it, and
  `useBoot()` prefers the live store once the client has synced — so the workspace renders
  fully on the server with no splash and no hydration mismatch.

`npm run verify` enforces all of this statically (plus client-bundle purity) so the bugs
cannot come back.

## What is actually implemented

Not a mock-up. Every button writes to the database, every generation enters the queue,
every asset lands in object storage.

## Architecture

```
Browser
  │  React 19 · Next 15 App Router · Zustand · TanStack Query · framer-motion
  │  canvas compositor ── WebGL grade pipeline ── Web Audio transport
  ▼
Next.js API routes ── one wrapper: auth → CSRF → rate limit → handler → envelope
  │
  ├─ Model Router ── capability detection → strategy/preset → credential check
  │                  → adapter → fallback chain → Demo engine
  │
  ├─ Job Queue ── durable records + in-process scheduler (or BullMQ/Redis)
  │                └─ Workers: image · video · audio · domain · export
  │
  ├─ Repository layer ── one interface, two drivers
  │        ├─ Prisma / PostgreSQL      (production)
  │        └─ embedded file driver     (zero-setup, multi-process safe)
  │
  └─ Storage abstraction ── one interface, two drivers
           ├─ S3-compatible (S3, R2, MinIO)
           └─ local filesystem, served via signed /authorised /api/files
```

### The provider abstraction

Nothing above the adapter layer names a vendor. Adding one is a catalogue row plus
one file — no UI, queue, storage or schema changes.

```ts
interface ProviderAdapter {
  driver: string
  capabilities(): Capability[]
  estimateCost(req, model): { credits: number; breakdown: string }
  generate(req, ctx): AsyncGenerator<ProviderEvent, GenerationResult>
  testConnection?(ctx): Promise<{ ok: boolean; message: string; detail?: string }>
  getStatus?(id, ctx)      cancel?(id, ctx)
}
```

Shipped drivers: `openai-compatible` (OpenAI, Azure, OpenRouter, Groq, vLLM, Ollama,
LM Studio), `anthropic`, `replicate`, `fal`, `elevenlabs`, `comfyui`, `custom-http`, `demo`.

**ComfyUI** is workflow-agnostic: paste a workflow exported in API format and map
`{{prompt}} / {{seed}} / {{width}} / {{height}}` tokens or explicit node ids. Any graph —
SDXL, FLUX, AnimateDiff, Wan, upscalers — runs unchanged.

**custom-http** lets you wire any REST API from the UI: method, headers, body template and
result paths (`result.imageUrlPath: "artifacts[0].url"`), including async job polling.

### Model router

`quality` / `speed` / `cost` / `explicit` / `preset` strategies, capability detection,
per-model credential resolution, reachability probing for local providers, and a
credential-aware fallback chain that always ends at the demo engine. If nothing can serve,
you get a message naming the providers that *could* — never a silent failure.

## Demo Mode is honest

The built-in engine is a real generator, not a placeholder:

- **Images** — deterministic SVG plates composed from the shot's own parameters: mood-keyed
  palettes, layered depth, haze, silhouette figures with rim light, bokeh, vignette, grain,
  lens-aware depth of field, and a baked-in `DEMO PLATE · NOT AI` badge.
- **Video** — a motion plate: a real sequence of generated key frames plus the camera move
  the shot asked for, played back by the compositor with zoom/pan interpolation.
- **Audio** — genuine DSP: biquad filtering, pink noise, comb reverb, additive synthesis.
  Rain, room tone, traffic, footsteps, doors, impacts, whooshes, fire, and a five-mood score
  engine, all written as real 16-bit stereo WAV files.
- **Dialogue** — a syllable-timed *scratch* track, labelled `SCRATCH` everywhere. It is real
  audio at the right length for timing a cut, and it never claims to be speech.
- **Upscale** — vector sources are rescaled losslessly; raster sources return the original
  with a logged warning rather than a fake upscale.

Demo assets carry `demo: true` through the database, the API, the UI and the export stage,
which warns you when a deliverable contains demo media.

```bash

# Object storage

AWS_ACCESS_KEY_ID=…  AWS_SECRET_ACCESS_KEY=…  AWS_S3_ENDPOINT=…   # R2/MinIO

# Security — REQUIRED in production
AFS_ENCRYPTION_KEY=<node -e "console.log(require('crypto').randomBytes(32).toString('hex'))">
AFS_SESSION_SECRET=<same>
AFS_AUTH_MODE=credentials        # open (default) = single local profile

# Platform-owned provider keys (server-side only, never sent to the browser)
OPENAI_API_KEY=…  ANTHROPIC_API_KEY=…  REPLICATE_API_TOKEN=…  FAL_KEY=…
```

The app refuses to guess about security: in production it logs a warning for every default
secret, missing database or local-only storage, and `/api/system` reports the same list.

## Security

- **Provider keys** (outbound) — AES-256-GCM envelope encryption, plaintext alive only inside
  the request that stores it. Responses carry a mask and a SHA-256 fingerprint. Keys are
  stripped from job payloads before they reach SSE. Never logged.
- **API keys** (inbound, for `/api/open/*`) — only a SHA-256 hash is stored, so a database
  leak yields no working credentials. Shown exactly once at creation, scoped, expirable, and
  revocation takes effect on the next request because there is no cache of valid keys. Issuing
  or revoking a key requires a session, never a key, so a leaked key cannot mint replacements
  and outlive its own revocation. All failure modes — unknown, malformed, revoked, expired —
  return one identical 401 so the endpoint cannot be used to probe which keys exist.
- **Authorisation** — every entity route resolves ownership through the parent project.
  Object storage requires an unexpired HMAC signature **or** a session that owns the object;
  a valid session alone is not enough.
- **Sessions** — `jose` HS256 JWT in an httpOnly, SameSite=Lax, secure cookie. Origin checked
  on every mutating request.
- **Rate limiting** — sliding window per user and IP, stricter bucket for generation, export
  and credential tests.
- **Uploads** — MIME allow-list, size cap, server-side metadata extraction.
- **Errors** — users get an actionable message and a suggestion. Provider messages and stack
  traces only appear with Developer Mode enabled.
- **Audit** — append-only trail of credential, billing, project and automation actions, with
  secret-shaped fields redacted.

## Public API

Everything the UI does over HTTP is also available to your own scripts under `/api/open/*`,
authenticated with an API key rather than a session. Create keys in
**Settings → Developer API**.

```bash
curl https://your-studio/api/open/system -H "Authorization: Bearer afs_…"
```

`x-api-key: afs_…` is accepted too, for clients that will not let you set `Authorization`.

| Endpoint | Scope | Purpose |
| --- | --- | --- |
| `GET /api/open/system` | `system` | Liveness, the calling key's name and scopes, capability enums |
| `GET/POST /api/open/projects` | `projects` | List or create projects |
| `GET/PATCH/DELETE /api/open/projects/{id}` | `projects` | Read, update (allowlisted fields) or delete one |
| `POST /api/open/generate` | `generate` | Enqueue a generation, returns a job. `{"dryRun":true}` prices it without spending credits |
| `GET /api/open/jobs`, `GET /api/open/jobs/{id}` | `generate` | Poll to a terminal state, then read `assetIds` |
| `GET /api/open/models` | `models` | Read-only registry: which models can serve which capability |
| `GET /api/open/assets` | `assets` | Asset library, filterable by project, kind and query |

Responses use the same `{ ok, data }` / `{ ok, error: { message, code, hint } }` envelope as
the session API, and errors translate identically, so one client parser covers both. A key
with no scopes reaches everything; a scoped key gets a `403 insufficient_scope` naming the
scopes it does have. Open routes are rate limited per key, so one runaway script cannot spend
the budget of everything else you do.

Generation is asynchronous by design — long renders never run inside a request:

```bash
JOB=$(curl -s https://your-studio/api/open/generate \
  -H "Authorization: Bearer $AFS_KEY" -H 'content-type: application/json' \
  -d '{"kind":"image","prompt":"a lighthouse in fog","modelId":"mdl_…"}' | jq -r .data.job.id)

curl -s https://your-studio/api/open/jobs/$JOB -H "Authorization: Bearer $AFS_KEY" | jq .data.status
```

The open surface is deliberately narrower than the session one. It cannot read or write
provider credentials, billing, team membership or other keys; it does not return
`readyProviders` (which would disclose which vendors this install holds keys for); and job
responses omit `input` and internal logs. Adding a route means adding a file under
`src/app/api/open/`, which is the entire audit surface — the wrapper is separate from the
session wrapper, so an internal route can never become key-reachable by accident.

## Scripts

```bash
npm run dev          # develop
npm run build        # production build
npm start            # serve the build
npm run typecheck    # tsc --noEmit
npm run worker       # standalone media worker (with AFS_WORKER_MODE=external)
npm run seed         # build a complete demo project through the real pipeline
npm run smoke        # 70-check end-to-end API test against a running server
npm run verify       # static architecture guards (see below)
npm run check        # verify + typecheck
npm run verify:open-api     # 101 checks on /api/open/* + the key lifecycle
npm run verify:comfyui-real # ComfyUI proxy against a real ComfyUI (see below)
npm run db:push      # prisma db push (PostgreSQL)
npm run db:studio    # prisma studio
```

`npm run verify` runs four static guards, each of which caught a real bug during
development: no client component may reach a `node:` builtin; no `instrumentation.ts` may
exist; no store selector may return a freshly-allocated reference; and boot data may only be
read through the SSR-aware accessors.

`npm run verify:open-api` boots the production build and drives the public API end to end:
every open route rejects an anonymous caller, a session cookie does not authenticate one,
malformed and revoked and expired keys are indistinguishable from outside, scopes are enforced
per route, and the plaintext key appears in exactly one response.

`npm run verify:comfyui-real` needs an actual ComfyUI checkout — no mocks, because a mock
written from the same reading of the docs as the code cannot catch a misreading of them:

```bash
COMFYUI_DIR=~/ComfyUI python3 scripts/comfy-fixtures.py   # seed models + workflows
python3 "$COMFYUI_DIR/main.py" --cpu --port 8188          # boot it
npm run verify:comfyui-real
```

`npm run smoke` exercises the whole product over HTTP — bootstrap, project creation,
story → script → cast → world → breakdown → plates → motion → voice → sound → assemble →
AI edit → versions → stems → bundle → queue semantics → credential encryption → router →
automation review gates → search → uploads → billing — and asserts that no raw key ever
appears in a response.

## Extending

**Add a provider.** Write one adapter implementing `ProviderAdapter`, register it in
`src/lib/ai/adapters/index.ts`, add `ProviderSeed` + `ModelSeed` rows in
`src/lib/ai/registry.ts`. Seeding is idempotent and never overwrites user edits.

**Add a node type.** Add to `NodeType`, handle it in `runNode()` in
`src/lib/automation/engine.ts`, add a palette entry in `NodeCanvas.tsx`.

**Add an edit intent.** Add a case to `expandEditOps()` in `src/lib/timeline/edit-ops.ts` —
both the demo engine and any LLM can then emit it, and it becomes a reviewable op.

**Swap the queue.** `AFS_QUEUE_DRIVER=redis` + `REDIS_URL`; the enqueue/observe surface is
unchanged. Or run `AFS_WORKER_MODE=external` with `npm run worker` today.

## Known limits

Stated plainly rather than papered over:

- **Server ffmpeg renders** need the binary; without it the API says so and points at the
  browser renderer, stems and bundles, which all work.
- **Browser export** renders in real time — a 3-minute film takes about 3 minutes — and
  produces WebM/MP4 depending on what the browser supports.
- **The embedded file driver** is single-host. It is multi-process safe (locked,
  merge-on-write) but not multi-instance; use PostgreSQL for that.
- **In-process SSE** assumes one web process. For multiple instances, back the bus with
  Redis pub/sub — `publish`/`subscribe` are the only two touch points.
- **Light theme** is stubbed; the product is designed dark.
- **Team seats** are modelled but single-profile in `open` auth mode.
- **Dev mode is memory-hungry** (~2 GB for the webpack graph). Production builds and runs
  comfortably in far less; see the note under Quick start.
